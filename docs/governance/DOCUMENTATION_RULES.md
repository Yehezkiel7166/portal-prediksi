# DOCUMENTATION RULES

Version: 1.0

Status: Approved

Owner: Project Owner

Last Review: 2026-07-21

---

# Purpose

This document defines the official documentation standards for Portal Prediksi CMS.

Documentation is considered part of the product and must evolve together with the implementation.

Every contributor is responsible for maintaining documentation quality.

---

# Documentation Principles

All documentation must follow these principles:

- Repository First
- Single Source of Truth
- Documentation Before Implementation
- Explicit Ownership
- Long-Term Maintainability
- Version Awareness
- Clear Traceability

---

# Repository as Knowledge Base

The repository stores permanent project knowledge.

Documentation must preserve:

- Product knowledge
- Business knowledge
- Engineering standards
- Security decisions
- SEO strategy
- Architecture
- Operational procedures
- Future planning
- Historical decisions

No important information should exist only in conversations.

---

# Required Documentation

Every significant change should update at least one of:

- Architecture
- Product
- Registry
- Governance
- SEO
- Testing
- Deployment

---

# Writing Standards

Documentation should:

- Use Markdown.
- Use descriptive headings.
- Be easy to navigate.
- Avoid duplicated information.
- Reference related documents where appropriate.
- Prefer explanation over assumptions.
- Keep terminology consistent.

---

# Naming Standards

Document names should:

- Use uppercase with underscores.
- Clearly describe their responsibility.
- Avoid ambiguous names.

Examples:

- MASTER_ARCHITECTURE.md
- FEATURE_REGISTRY.md
- SEO_ARCHITECTURE.md

---

# Versioning

Each document should contain:

- Version
- Status
- Owner
- Last Review

Major revisions should increase the version number.

---

# Change Management

Whenever documentation changes:

- Verify related documents.
- Update cross references.
- Preserve historical context when necessary.
- Avoid conflicting information.

---

# Documentation Lifecycle

Every document follows this lifecycle:

1. Draft
2. Review
3. Approved
4. Active
5. Deprecated
6. Archived

---

# Responsibilities

Project Owner:

- Approves strategic documentation.
- Defines priorities.
- Reviews major changes.

Engineers:

- Keep implementation synchronized.
- Update documentation after changes.
- Preserve architectural consistency.

---

# Review Process

Documentation should be reviewed whenever:

- New modules are added.
- Architecture changes.
- Security changes.
- SEO strategy changes.
- Major features are introduced.
- Product direction changes.

---

# Quality Checklist

Before considering documentation complete, verify:

- Purpose is clear.
- Scope is defined.
- Responsibilities are explicit.
- Cross references are correct.
- No duplicated content exists.
- Terminology is consistent.
- Version metadata is updated.

---

# Documentation Philosophy

Documentation is an engineering asset rather than a project artifact.

Its purpose is to preserve knowledge, reduce ambiguity, support future development, and minimize dependency on individual contributors.
